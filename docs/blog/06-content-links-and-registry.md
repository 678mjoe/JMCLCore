# 内容管理不是复制文件：硬链接、登记表与版本切换

同一个模组可以在实例 A 中启用，在实例 B 中禁用，也可以在实例 C 中换成新版本。
底层字节能够共享，管理状态却不能共享。那么，文件和登记表分别表达什么事实？
更新失败时，哪一份状态已经改变？

本文沿着[硬链接存储](01-hardlink-storage.md)继续讨论内容管理。以下行为来自固定
Zig 基线 `5a4310d`；对取舍的解释是技术分析，不是未被记录的作者决策史。

## 一份内容，两种身份

在文件系统里，一个下载文件以 SHA-1 对象的身份进入 CAS；在实例里，它又以
`mods/example.jar` 等路径出现。通常二者是同一 inode 的硬链接。登记表保存的
则是另一层信息：内容类别、文件名、摘要、来源项目与版本、是否启用、是否作为
依赖安装。它不是把 CAS 变成可随意改写的工作目录。

因此，有两种完全不同的“更新”：登记表属于实例的可变状态，以临时文件加原子
替换写入；不可变内容则先验证再发布，通过链接或替换目录项交付。不能为了实现
一个方便的更新按钮，就在已有硬链接上原地写入新字节——那会同时改变其他实例
看到的同一份对象。跨设备等情况沿用原实现的回退规则，不把复制变成默认路径。

## 收编文件不等于复制文件

`adoptInstanceContent` 先列出尚未登记、扩展名匹配的普通文件，计算摘要和大小，
导入 CAS，再把原实例路径交由 CAS 物化，最后写登记表。来源被标为 `manual`。
这意味着既有手工安装也能加入同一套存储模型，而不是形成一条永久的重复存储路径。

移植中一个很小的边界值得记录：原实现的扫描可以读取内容目录的符号链接别名，
但随后 CAS 对相对路径的遍历拒绝该别名。若 Rust 先取得子目录句柄，再把它当作
新的 CAS 根，就会让原本失败的收编成功。安全的句柄操作并不自动等于兼容的操作；
必须保留正确的根边界。差分测试用临时目录明确验证了这一点。

## 换版本时，旧链接最后才离场

原 `setInstanceContentVersion` 不是先删旧文件再下载：它先解析新版本、检查
项目归属和兼容性、验证目标文件冲突，再通过安装器交付新对象。如果内容已禁用，
新文件继续保留 `.disabled` 状态。登记表替换成功后，才删除旧文件名。

“禁用”因此主要是目录项的变化，不需要重写文件，也无需破坏 CAS 对象。重复
切换到同一版本是无网络的 no-op。这里也不应夸大原行为：多文件安装失败时可能
留下已完成的物化文件；登记表在整个计划完成后发布，并非文件系统级全事务回滚。

## Provider 与内容字节是两个边界

Modrinth/CurseForge 负责发现项目、挑选版本和依赖；安装器只接收 URL、摘要、
长度与目标路径。CurseForge API key 留在调用者与元数据请求之间，不进入下载
计划、登记表、事件或 CDN 请求。Rust 的请求解析使用借用 JSON 与擦除型解码
缓冲区；HTTP 库内部可能另行分配头部存储，因此不能据此声称所有凭据分配都可
保证擦除。

重写的证据也必须分层：原始 Zig 二进制验证无网络错误路径；纯 schema 适配器
验证解析与选择；替换了**且只替换了**元数据 fetch 的独立测试副本验证成功安装、
事件顺序和磁盘状态。测试副本记录源码、补丁和生成物来源，不能冒称未经修改的
线上 oracle。原生 Windows、真实网络错误与重定向仍要分别验收。

参照：原 `src/service.zig` 的 `adoptInstanceContent`、`installResolvedContent`、
`resolveModrinthContent`、`resolveCurseforgeContent` 和
`setInstanceContentVersion`；Rust 对照实现在 `rust/src/content/`。
