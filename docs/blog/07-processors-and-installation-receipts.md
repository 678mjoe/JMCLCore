# 下载完成，不等于安装完成：处理器与硬链接存储

Forge 和 NeoForge 的现代安装包不只是文件清单，还描述了一条处理器流水线：输入游戏文件、补丁和工具库，运行 Java 工具，生成真正参与启动的产物。这篇文章记录从固定 Zig 源码还原的行为，不替原作者编造未被记录的决策动机。

## 两种产物，一套存储哲学

下载来的不可变文件可按已知 SHA-1 校验、进入 CAS，再硬链接到实例。处理器输出则尚不存在，有时还没有预先声明的最终摘要。

原实现没有给生成产物另开一套长期存储体系。处理器完成后，Core 计算生成文件摘要；Forge 声明了摘要时还会核验它。随后生成文件同样进入 CAS，并重新投影为实例中的硬链接。

这延续了项目的核心初衷：实例隔离版本和可变状态，相同的不可变字节尽量只保留一份。**硬链接不只是下载缓存的细节，也覆盖本地产生的可复用产物。**

## 不把缓存策略「优化」成另一个协议

固定 Zig 基线不逐个处理器跳过。它的快捷路径是整条流水线的 `state.json`：记录最终产物 SHA-1 与长度，下次验证仍匹配，就跳过整条链。

重写不能因为另一种策略看起来更聪明，就悄悄采用它。逐步骤跳过会改变工具调用次数、事件顺序、错误暴露位置，以及对旧实例已有状态文件的解释。

因此 Rust 保留整链缓存、client/server 筛选和原始顺序。先发进度事件，再检查依赖、解析 Main-Class、替换参数并执行。服务层依旧在调用处理器之前按 Java 策略选择运行时；缓存跳过的是处理器内部二次探测，不是服务层选择。

## 状态文件就是承诺

「下载成功」「处理器成功」「安装完成」是三个不同事实。

处理器失败时，验证过的下载对象可以留在 CAS 供重试利用，临时 work 目录则清理。最终产物验证、CAS 导入和重新投影成功后，才能写处理器状态。整个调用成功后，外层才能写 `.jmcl/install.json`。

无法取得所需 Java 也不应包装成一次成功安装。本切片只使用本地或已安装的受管 Java；尚不可用的受管 Java 获取路径明确失败，不生成成功收据。

## 差分测试发现的生命周期缺陷

测试使用手工构造的小型 ZIP 和无害的原生「假 Java」，比较固定 Zig 基线与 Rust 的事件、错误、输出与状态文件，没有下载真实加载器或启动游戏。

测试发现了一个不属于业务设计的基线缺陷：原 RPC 把处理器摘要切片留给最终响应，却在离开条件分支时先释放了切片。结果是响应没有携带有效的 SHA-1 字符串。这里需要解释的是所有权边界，而不是把错误字节固化成业务协议。

Rust 保持摘要所有权直到响应写完，不复制已释放内存的读取。这一修正符合已获批准的、有源码和测试证据的缺陷处理原则，并单独登记在
[原版缺陷台账](../rewrite/original-core-defects.md)；其它字段仍严格比较。批准修正
不意味着字节完全一致，不允许把所有不一致解释为改进，也不意味着自动修改 Zig 主线。

源码基线：`5a4310debbcee26b3d2391bab2339f79cd6ec52e` 的 `src/loaders/{neoforge_executor,forge_executor}.zig`、`src/protocol/install.zig`、`src/cli/install.zig`。相关行为由[处理器差分测试](../../rust/tests/loaders_differential.rs)记录。
