# 让实例共享文件本体：JMCL Core 的硬链接存储

*技术文章草稿。实现参照：Zig Core `5a4310d`。本文讨论已有设计及其在
Rust 重写中的约束，不声称 Rust 版本已经完成。*

Minecraft 庞大的模组生态催生了大量整合包，也让多个实例并存成为自然需求。
这些实例可能基于同一个 Minecraft 版本、同一种模组管理器，并共用许多模组；
但为了保持各自的版本和组合，它们仍然需要隔离。

项目作者说明，这正是选择硬链接的起点：传统的多实例、版本隔离模型会让同一份
文件在大量实例中留下大量副本。目标是在维持版本隔离的同时，尽量节约磁盘空间。
硬链接式文件管理因此成为项目的初衷和首要设计约束，而非后来追加的缓存优化。

这里要分别处理两件事。实例的目录关系、版本选择和可变状态需要独立；内容完全
相同的不可变文件，却不必因此占据多份磁盘空间。JMCL Core 用硬链接把这两层
分开，让隔离继续存在，同时允许文件本体被共享。

普通下载缓存可以减少重复联网，但只要安装阶段仍向每个实例复制一遍，共存实例
的重复存储问题就没有消失。这是对实现差异的分析，不代表作者曾明确考察并否决
某一种特定缓存产品或其他方案；目前没有这样的历史材料。

## 从文件名转向内容身份

同一个文件可能来自不同 URL，出现在不同版本的目录里；相同的文件名也不保证
内容相同。JMCL 使用经过尺寸和 SHA-1 验证的内容作为共享对象的身份：

```text
.jmclcore/objects/sha1/ab/abcdef...
```

前两位十六进制字符用于分散目录条目，完整的小写摘要是对象名。安装器再把对象
放到 Minecraft 期望的位置，例如某个实例的 libraries 或 assets 目录。
在支持的文件系统上，这一步创建硬链接，不重新复制字节。

这里的 SHA-1 与 Minecraft 上游元数据的制品身份保持一致。它不是签名，不能
凭空让不可信元数据变可信；重写也不能为了“换一个更新的哈希”而悄悄改掉对象
地址，使用户已有的共享存储失去意义。

## 硬链接的收益，来自必须守住的边界

硬链接不是指向另一路径的快捷方式。两个目录条目引用同一文件，因此删除一个
实例里的链接，不会立即删除另一个实例仍在使用的内容。这使多实例复用不仅
发生在下载阶段，也延续到安装后的磁盘布局。

代价同样直接：经由任意一个链接修改文件内容，会影响其他链接看到的内容。
所以“共享不可变制品”和“实例私有的可变状态”必须一起设计。

客户端 JAR、库、资源、原生库归档以及受管理的不可变内容包可以复用对象。
存档、日志、截图、选项和配置则属于实例自己。后来增加的 Modrinth 内容管理
也复用了内容寻址机制；不能因为某篇早期文档曾把整个 mods 目录排除，就把
当前所有受管理的 mod 归档都误认为必须复制。真正要区分的是文件的生命周期，
不是仅凭目录名下结论。

现有实现把发布后的共享对象设为只读；修复或升级采用完整的新对象，再替换相关
实例的目录条目，而非原地改写共享字节。只读属性是防误写的一层保护，不能把它
描述为能抵御一切同权限程序的安全沙箱。

## 安装器需要知道何时可以相信一个文件

“磁盘上已经有文件”不是缓存命中的充分条件。安装器先核对尺寸与摘要，按摘要
获取对象锁，再检查共享对象。已有实例文件正确而共享仓库缺失时，可以反向导入；
否则下载到临时文件，校验完整后发布。

锁按对象身份划分，而不是给整个仓库加一把大锁。相同对象的发布需要协调，不同
对象仍可并行处理。这是根据实现能够看出的并发取舍；没有额外证据时，不应把
它写成作者当时明确比较并否决所有其他锁策略的历史。

“尽量原子”也需要细分路径。macOS/Linux 的硬链接物化先在目标目录创建临时
链接，再重命名到最终位置。Windows 有单独的替换路径。跨卷、不支持硬链接、
链接配额或权限限制时，现有实现回退到复制，而这条回退不是原子替换。
因此中断后的正确承诺是重新校验并恢复，不是“随时杀进程都完全没有影响”。

## 垃圾回收利用了文件系统已经知道的信息

如果一个共享对象只剩仓库自己的链接，就可能成为可回收对象。JMCL 的 GC
默认只预览，并设有保留时间；实际删除会使用与安装相同的摘要锁，检查规范路径、
文件类型和链接计数。

这不是按实例清单计算可达性的数据库垃圾回收。外部硬链接也可能保留对象；
跨卷复制出来的实例文件不会增加共享对象的链接计数，因此不能阻止对象被回收。
但对象被回收并不会让那些独立副本失效。这些边界应当直接写进使用说明，而不是
用一句“自动清理未使用文件”盖过去。

历史记录可以确认：初始提交已经含有共享制品存储；紧接着的 GC 提交明确选择了
`nlink == 1`、逐对象锁、默认预览以及 Windows 句柄安全。再之后，内容管理把
同一存储思路扩展到 mod 归档。它逐渐成为多个功能共享的基础，而非孤立的缓存技巧。

## Rust 重写应该证明什么

重写可以改变内部模块和资源管理方式，不能把核心模型换掉。存储测试必须
验证“两个路径确实指向同一文件”，而不仅是“读出的字节一样”：Unix 检查设备与
inode，Windows 检查文件身份；随后验证更新或删除一个实例的文件引用不会破坏另一个实例、可变数据仍然隔离、损坏对象
不能作为命中复用、允许的复制回退有明确记录，以及旧布局无需迁移即可读取。

还需要检查 Zig 与 Rust 对同一摘要锁的互操作，避免两个版本并存时各自以为已经
独占对象。仅仅保持锁文件名相同不够，实际锁机制也必须一致。

文章写到这里，重写的验收目标已经具体了：让语言变化留在实现内部，让用户已经
建立的实例关系、文件身份和共享收益继续成立。[契约篇](02-rewrite-without-changing-contract.md)继续解释这些目标如何转化为
可执行的对照；[发布事务篇](05-hardlink-publication-transactions.md)再展开锁的边界。
已有测试代码不免除平台验收，也不能先宣布兼容，再寻找证据。
