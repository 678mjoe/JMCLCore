# 同一份模组，许多个实例：整合包如何保持隔离，又不重复占盘

JMCLCore 的出发点不是换一种下载器。Minecraft 的模组生态会自然产生许多实例：同一个 Minecraft 版本、相同的加载器，以及部分相同、部分不同的模组组合。传统的版本隔离通常把整个目录复制一遍；隔离做到了，但相同文件也被重复存储了。

项目作者明确给出了这项设计的背景：希望在维持版本隔离的同时尽量节约磁盘，因此选择硬链接。这是原项目的初衷，不是 Rust 重写新加的优化。

## 共享的是不可变字节，不是可变实例

一次整合包导入可以分成两类文件：

- 下载清单里的内容文件：经过大小和 SHA-1 校验，存入内容寻址存储（CAS），再硬链接到实例目录。两个实例引用同一内容时，目录项不同，底层文件字节可以相同。
- overrides：整合包带来的配置等文件，作为实例私有的可变状态写入。它们不能被当作共享对象原地修改。

这个区分比“用了硬链接”本身更重要。硬链接不是写时复制。如果直接打开实例里的共享 JAR 并截断，其他实例和缓存都会看到变化。因此替换要发布一个新的文件，再替换目录项；不能写穿旧 inode。

Rust 的测试专门覆盖了一个容易忽略的情况：整合包先下载 `mods/a.jar`，随后 overrides 又提供同名文件。导入必须让该实例得到私有的新文件，而 CAS 和另一实例仍保留原始字节。这里用的是原子替换，不是覆盖写入。内容登记仍按原项目的顺序在 overrides 之前保存；重写不会顺手发明一种新登记格式。

## 安装整合包不等于安装游戏

原项目的 `modpack.install` 创建实例、准备整合包内容、保存内容登记并展开 overrides。它不会顺便安装 Minecraft 客户端和加载器的全部游戏文件；后续仍走通常的实例安装流程。

这个边界容易在重写时被“改善”掉，却会改变调用者观察到的行为。Rust 保留这个边界，也不新增一个原协议里没有的 inspect RPC。检查和计划是内部模块，用来让行为更容易测试。

## 失败后留下什么

原实现采用一个清晰的事务边界：导入失败，删除本次刚创建的实例；已经验证并发布到 CAS 的对象可以留下。修复问题并重试时，这些对象可以直接复用。

因此，“恢复”不必意味着新增一个持久化任务清单。现有的恢复机制是实例回滚加上可复用的内容缓存。新增加的任务状态文件反而会扩张磁盘格式，破坏无需迁移的接管目标。

## 两种包格式，不强行统一所有语义

Modrinth 包显式标为客户端不支持的文件会跳过，optional 文件则仍安装；CurseForge 包的 `required: false` 文件会跳过。这不是对称的规则，但这是兼容性的一部分。

Modrinth 下载列表只使用前两个 URL，分别作为首选与备用；CurseForge 文件缺少直链时，会额外请求下载地址。CurseForge API 密钥由调用方提供，不进入实例清单、内容登记和下载计划，也不会随 CDN 下载发送。

这些细节提醒我们：重写的任务不是把原设计翻译成看起来更整齐的 Rust，而是先理解它服务于哪些边界，再以可以验证的实现保留这些边界。

## 本文的证据边界

作者动机来自本次讨论；具体行为来自固定的 Zig 基线 `5a4310debbcee26b3d2391bab2339f79cd6ec52e` 的 `src/service.zig`、`src/modpack/` 与 `src/protocol/modpack.zig`。我们没有把代码结构推断成未证实的历史决策。离线测试可以验证协议、文件布局、硬链接和失败回滚；真实服务可用性、跨卷行为以及各平台运行仍需要相应环境的证据。
