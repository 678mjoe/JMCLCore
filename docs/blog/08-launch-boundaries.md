# 从硬链接仓库到进程：启动边界为什么值得保留

重写一个启动器内核，容易把“启动”理解为拼接一行 Java 命令。JMCLCore 的原实现实际上保留了几条更重要的边界。本文根据固定的 Zig 基线 `5a4310d` 的 `src/launch/plan.zig`、`src/launch/process.zig`、`src/launch/executor.zig` 和 `src/install/preparer.zig` 总结；下面的工程解释是从实现推导出的理解，而不是替原作者补写未经确认的历史动机。

## 隔离的是实例，复用的是不可变字节

项目的出发点是大量 Minecraft 实例共存时，同版本、同加载器和相同模组造成的磁盘重复。硬链接让不同实例保留各自目录布局，却共享相同的不可变文件。实例安装必须经过验证、发布和物化的同一条路径，不能因为它只是一个 CLI 包装层，就退回逐文件复制。

因此 Rust 的 `instance install` 并没有另外实现一个下载器：它读取已固定版本的实例清单，再交给全局安装器。测试让两个实例只获取一次相同的模拟文件，验证两个实例文件和 CAS 的 inode 关系；错误内容则既不能发布，也不能留下“安装完成”的凭据。安装凭据是完成的证据，不是下载开始的承诺。

## 临时 native 文件不是新的共享资产

启动准备会提取 native 库、布置旧版本资源映射，再创建本次运行独享的 native 目录。它不把运行期产生的可变内容重新导入 CAS。这个区分很重要：共享不应扩展到任何碰巧位于实例目录中的文件，否则一个实例的修改可能影响其他实例。

Rust 用持有打开目录句柄的清理守卫表达这一生命周期。Java 选择失败、启动计划失败、进程创建失败、正常结束和提前丢弃守卫，都需要清理本次 native 目录；绝对路径从已打开的目录句柄取得，而不是重新相信可能已经被替换的外部路径。

## 参数是数组，不是一段 shell 程序

原始启动计划区分现代参数规则、旧版引号分词和调用者提供的字面量附加参数。替换 `${...}` 并不意味着再交给 shell 解释。带空格的名字、分号、美元符号和空字符串都必须保留自己的参数边界。

这里的兼容性也不是“换一个正则库”：原项目使用受限的字节模式匹配器，接受和拒绝的表达式集合本身就是可观察行为。Rust 保留这套规则，并直接比较两端完整计划与错误，而不是只验证最终 Java 进程是否能够运行。

## 不把可执行参数当作调试输出

真实 argv 需要包含认证字段，但启动事件只能携带脱敏后的参数。Rust 采用单一擦除所有者保存展开的参数；请求解码和结果输出不绕道包含令牌的通用 JSON 树。子进程输出在分块边界之间持续脱敏，然后按原协议发送带序号和结束类型的 base64 记录，避免用文本假设破坏二进制输出。

这不是“所有内存都必然擦除”的声明：操作系统参数区和标准库进程内部缓冲不在这个保证内。原实现的模板／子串敏感字段规则也不是万能秘密识别器。

## 发现缺陷不等于可以悄悄改变协议

继承 stdout/stderr 的后代进程可能让旧实现等待 EOF 很久。实验性 Rust 运行器在直接子进程退出后有界排空已可读数据，避免无限等待；但这也可能不再收集后代之后写出的内容。这是明确记录的行为差异，不是一个被包装成“兼容性通过”的改进。项目已批准对源码和测试证实的旧缺陷记录例外、保留正确行为；这项差异及其代价
仍须进入[原版缺陷台账](../rewrite/original-core-defects.md)，不能因此删除严格对照
或放宽无关行为。完整替换的其他门槛依然存在。

同样，当前已验证的是本地和已经安装的 Java 运行时路径。缺少托管运行时下载能力时必须返回失败，不能拿一个空成功结果填补路线图。边界清晰，才知道硬链接、隔离、兼容与安全各自在保护什么。
