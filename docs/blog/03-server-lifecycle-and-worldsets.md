# 请求结束之后，服务器为什么还在运行？

*技术文章草稿。实现事实以 Zig Core `5a4310d` 的
`src/server/lifecycle.zig`、`src/server/server_store.zig`、
`src/service.zig` 与 `src/worlds/worlds.zig` 为依据。Rust 对应实现位于
`rust/src/servers/` 与 `rust/src/worlds/server.rs`。下文的取舍解释属于设计分析，
不冒充作者当时未记录的决策过程。*

## 一次命令，两个生命周期

JSONL 请求、终端和 SSH 会话都可能很短；Minecraft 服务端却可能运行很久。
如果启动器把 JVM 的存活时间绑在发出请求的进程上，“启动成功”也可能只意味着
它恰好还没遇到终端关闭。

现有 Core 把控制请求与监督进程分开。启动请求先持有生命周期锁，再运行
`__server_bootstrap`。bootstrap 创建独立会话，启动
`__server_supervisor`；supervisor 启动 JVM、记录状态并返回一次握手。
请求进程结束后，监督进程继续读取 JVM 的标准输出和标准错误，把它们写进
`logs/console.log`，并通过 `.jmcl/console.fifo` 提供控制台输入。

这里的“独立”是进程会话与标准流的独立，不是声称具有 systemd 那样的服务恢复、
机器重启自启或任意容器销毁后的存活能力。Rust 测试用无害的 shell 子进程验证了
**发起 JSONL 请求的进程已经退出，随后仍能查询状态、发送命令和停止服务**；
没有拿真实 Minecraft 服务端或用户的 SSH 会话做实验。

## PID 不是身份证

`.jmcl/server.pid` 不只记录 PID。它还保存监督进程 PID、Java 路径、启动时间和
随机身份值。启动 JVM 时，身份值成为一个完整参数：

```text
-Djmcl.server.identity=<128-bit random token>
```

检查是否仍在运行时，Core 在 Linux `/proc/<pid>/cmdline` 中查找这个**完整参数**。
只看 PID 会把进程号复用误认为原服务端仍在运行；只看 Java 文件名，也无法区分
多个实例。随机身份值把磁盘状态与某一次具体启动关联起来。

这不是对同一用户下恶意进程的认证协议：同权限进程可能读取参数和状态。
它解决的是正常生命周期中的身份混淆。Rust 的测试特意把状态文件中的 PID 指向
测试进程本身，却使用不匹配的身份值；停止操作清除过期状态，而不向该进程发信号。

## 停止不是立即 kill

原实现的停止次序是：

1. 向 FIFO 发送 `stop`，等待请求指定的宽限期；
2. 若对应身份的进程仍存在，发送 `SIGTERM`，再等五秒；
3. 仍未退出时发送 `SIGKILL`，再等两秒。

返回值区分 `graceful`、`terminated` 与 `killed`。启动、停止、重启和“必须停止后
才能执行”的操作共用 `.jmcl/lifecycle.lock`。`lockStopped` 返回的是持有锁的守卫，
而不只是一次布尔检查：检查结束后，锁要一直覆盖安装、属性修改或世界修改，
否则另一个请求可以在“检查已停止”和“开始写文件”之间启动服务。

Rust 使用三个无害进程场景验证正常停止、忽略控制台停止、再忽略 `SIGTERM` 的升级
路径。这验证了有限场景中的次序与结果，不证明所有故障和调度情形已经覆盖。

## 日志游标要能识别轮转

日志最多保留当前文件与两个轮转文件。客户端读取日志时，不只传字节游标，还传
文件身份 `file_id`。游标越界、缺少身份或 inode 不匹配时，Core 回退到当前日志尾部，
并报告 `reset`。否则日志轮转后，一个看似合理的旧偏移可能对应完全无关的内容。

读取结果还要保护 UTF-8 边界：从半个字符中间开始时跳过开头的续字节，末尾不完整
的字符留待下次读取；真正的内部非法编码则报告失败。Rust 已有对应的边界、轮转、
叶节点符号链接拒绝与读取上限测试。

## 共享制品，不共享可变世界

项目作者已经说明，硬链接式文件管理的初衷是让大量隔离的 Minecraft 实例共享
相同文件的本体，减少重复占用。这一哲学并不意味着“所有文件都硬链接”。

服务端制品可以经过验证进入不可变内容存储；世界数据、属性、日志和生命周期状态
却会变化。世界复制和恢复仍使用独立字节，不把它们发布为 CAS 硬链接。
这个边界让节省空间与隔离性同时成立：复用的是相同制品，不是不同实例的游戏进度。

服务端还有一层不能丢掉的关系：`server.properties` 的 `level-name` 指向基础世界，
旁边可能存在 `<name>_nether` 与 `<name>_the_end`。改名基础世界时，要同时处理这些
维度目录并更新属性；删除基础世界时，要处理它们；默认备份也包含这组目录。
显式指定单个世界备份则只选择该世界。

Rust 把这些操作绑定在已经打开的目录句柄上，并让停止守卫覆盖整个操作，避免先
检查一个路径、再重新打开另一个同名路径。恢复保留原实现的**逐个世界发布与单步
回滚**语义；它不是整组世界的全有或全无事务。不能因为“重写了”就把原本没有的
原子性写进承诺。

## “创建了”不等于“安装好了”

原实现把服务端配置、用户同意与安装完成分成了三件事。创建会先解析版本和加载器，
再写 `server.json`，不会因为创建成功就声称已经拥有可启动的服务端。安装请求必须
明确传入 EULA 同意；获得停止守卫后，这份同意先写进清单。随后计划或 Java 选择
失败，并不会撤销已经表达的同意。`eula.txt` 则在制品完成物化之后才写入。
这看起来有点“不对称”，但记录的是不同事实：用户作出了选择，与文件准备完毕，
不是同一个事务。

不可变的 `server.jar` 和库通过校验、CAS 与硬链接复用；`eula.txt`、默认属性、Fabric
启动参数和安装记录则使用私有文件原子替换。已有属性文件保持原样，而不是每次
安装都覆盖用户配置。这里延续了项目的核心边界：共享不变的内容，不共享可变的
实例状态。

Fabric 不能直接拿客户端配置启动服务端。它使用独立的 server profile、服务端
入口类与确定顺序的参数文件。现代 Forge/NeoForge 在下载之外还需要处理器链，
并验证最终启动参数文件。最后才写 schema-3 安装记录；下载成功并不等于处理器
成功，更不等于已经可以启动。中途失败可以留下已验证的共享制品用于重试，但不能
伪造一份“安装完成”的凭据。

这段迁移首先用缓存中的人工元数据、几字节的制品与只输出版本属性的探测程序验证：
成功路径、错误顺序、配置保留、硬链接与私有文件边界、最终记录内容。它们证明的是
协议与状态机，而不是某个真实整合包已经经过生产验证。

## 重写要证明什么，又还没证明什么

实现保留了原来的目录、状态记录、随机身份参数、FIFO、日志游标与世界耦合关系。
测试包括独立请求进程退出、控制台命令、重启、三段停止、锁保护、世界备份恢复，
以及固定 Zig 基线下的有限 RPC/CLI 差分矩阵。

这些不是“Rust 已可替换主线”的宣告。真实 Minecraft 负载、长时间运行、SSH 环境、
非 Linux 服务端适配仍不能由上述本地测试代替。尤其原 Zig 的世界列表、详情、备份
列表与备份删除 CLI 不经过 Linux 生命周期检查，而 RPC 有统一的平台门禁。Rust
为这些 CLI 路径接入了可移植的目录句柄适配器；需要停止守卫的操作仍在检查服务端
后进入平台限制。跨平台差分测试必须在对应平台实际运行，不能用一句“服务端只支持
Linux”抹掉这些差异，也不能把 Linux 测试算作 Windows 或 macOS 的运行证据。

更换语言时，最容易遗漏的往往不是某个函数，而是函数之间的约定：请求与服务的
寿命不同，PID 与启动身份不同，制品与世界的可变性不同，单步回滚与全事务也不同。
把这些区别记录下来，才是让下一次维护不必重新猜一遍设计的价值。
