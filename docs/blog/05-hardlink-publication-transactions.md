# 为什么“下载完成”还不够：硬链接管理中的发布事务

## 从多实例的浪费说起

项目作者给出的出发点很具体：Minecraft 的模组生态和整合包让大量实例并存；
实例之间需要版本隔离，但相同游戏版本、加载器和模组不应该反复占用磁盘空间。
因此，硬链接不是后来加上的缓存优化，而是文件管理模型的起点。

下面讨论的是 pinned Zig 实现与 Rust 重写中的可观察机制，不把实现推断冒充作者
当年的决策记录。参考基线为 `5a4310debbcee26b3d2391bab2339f79cd6ec52e`。

## 文件名隔离，不等于每份内容都要复制

一个实例仍然拥有自己的 `versions/`、`libraries/` 和资源路径。相同内容则通过
SHA-1 对象地址进入共同仓库，再以硬链接放到各自的路径。目录布局和版本选择保持
独立；同一个对象的磁盘数据可以共享。这里沿用 SHA-1 是磁盘与协议兼容要求，
并不意味着把 SHA-1 宣称为新的抗恶意碰撞设计。

硬链接也不是通用的写时复制。两个链接指向同一个 inode，原地写入会影响所有链接。
所以管理器必须区分不可变下载对象和可变内容。Rust 的 `atomic_replace` 写入新文件，
同步后再替换目标路径，绝不截断可能已经连到 CAS 的 inode。原有实例和仓库对象因而
不受这次替换影响。只读权限有帮助，但不能阻止有权限的外部程序强行改写；这仍然是
模型的使用边界，不能被描述成对任意外部写入都透明安全的文件系统。

## 真正的事务终点是“实例已经持有链接”

最容易遗漏的竞争不是两个下载器，而是下载器和垃圾回收器：

1. 下载器完成校验，把临时文件发布成仓库对象。
2. 如果此时释放对象锁，再去建立实例链接，就出现了空窗。
3. GC 看到一个尚无实例链接的对象，可能把它当成无引用对象删除。

因此事务应覆盖“检查缓存 → 清理损坏对象 → 下载/导入 → 发布 → 物化实例路径”。
Rust 的 `ObjectTransaction` 把仓库和摘要身份绑定在一个不可伪造的 guard 上；暂存
对象借用这个 guard，不能比锁活得更久。已有的自动加锁方法不能再包一层相同的锁，
否则可能自我死锁。这里重要的不是锁更多，而是让锁的边界对应业务不变量。

## 校验、重试、进度是三个不同问题

下载先进入私有暂存文件，大小与摘要均符合计划后才发布。一次失败的尝试可以已经
产生大量流量，但它不能被算成成功下载；重试的进度也不应把同一文件反复累加到超过
总量。实现分别记录成功传输字节、已验证字节，以及按文件取最大值的处理进度。

终端输出同样会失败。RPC 的事件写入保持在调用者线程；工作线程通过容量为零的
事件通道和确认通道等待结果。输出失败后，等待中的线程得到失败确认并收尾，而不
是在没有实际完成安装的情况下输出成功回执。

## 原生库为什么不继续塞回共享仓库

下载的原生库归档可以作为不可变对象共享；解压后的运行时目录则属于本次准备流程。
归档先整体预检：路径、类型、重复输出、大小、压缩比例都必须符合约束，然后才进入
独立的随机 native 目录。失败时清理该目录，不污染其他实例的运行时状态。

兼容重写也会发现历史瑕疵。基线的 native 解码没有验证实际数据 CRC；当前兼容实现
没有悄悄把“更严格”包装成“完全一致”。这类变化需要独立、明确的缺陷修复决定。

## 什么证据能支持这些说法

测试不只比较返回值：它检查真实 inode 共享、并发写入与 GC 排斥、错误后的锁释放、
替换可变文件后旧内容仍然不变，以及无跟随目录句柄下的路径边界。有限的 Zig 对照
用例还比较事件顺序、回执字节和解压结果。它们不是生产上游可用性证明，也不能替代
Windows 原生执行验收。
